# Выбор и настройка мониторинга в системе

## Мотивация

**Проблема**: теряем заказы, не знаем где именно
- Клиенты жалуются на потерянные заказы
- Крупные контракты потеряны из-за проблем с заказами
- Не видно, где именно падают заказы: Shop -> RabbitMQ -> CRM -> MES
- Яндекс Метрика показывает только фронтенд, API-заказы не видно

**Что даст мониторинг**:
- Видим, где теряются заказы (RabbitMQ, БД, API)
- Можем найти узкие места до того, как система упадет
- Алерты при проблемах - узнаем раньше клиентов
- Метрики для обоснования масштабирования

**Для бизнеса**:
- Меньше потерянных заказов = больше денег
- Быстрое реагирование на проблемы = меньше жалоб
- Прогнозирование нагрузки = контроль затрат на инфраструктуру
- SLA для партнеров = можем гарантировать доступность

## Выбор подхода к мониторингу

### RED метод (для всех API)
Используем для Shop API, CRM API, MES API

- **Rate** - запросов в секунду
- **Errors** - процент ошибок
- **Duration** - latency запросов

### USE метод (для инфраструктуры)
Используем для БД, RabbitMQ, инстансов

- **Utilization** - загрузка
- **Saturation** - очереди и перегрузки
- **Errors** - ошибки

## Метрики

### API метрики (RED)

#### RPS для всех API
**Зачем**: видим нагрузку, аномалии, планируем capacity

**Метрики**:
- Number of requests (RPS) for internet shop API
- Number of requests (RPS) for CRM API
- Number of requests (RPS) for MES API

**Ярлыки**:
- `service`
- `endpoint`
- `method`
- `status_code` 

#### Response time (latency) для всех API
**Зачем**: находим медленные запросы, нарушения SLA

**Метрики**:
- Response time (latency) for shop API
- Response time (latency) for CRM API
- Response time (latency) for MES API

**Ярлыки**:
- `service`
- `endpoint`

#### Number of HTTP 500 для всех API
**Зачем**: видим процент ошибок, триггер для алертов

**Метрики**:
- Number of HTTP 500 for shop API
- Number of HTTP 500 for CRM API
- Number of HTTP 500 for MES API

**Ярлыки**:
- `service`
- `endpoint`
- `error_type`

#### Number of HTTP 200 для всех API
**Зачем**: для рассчета % ошибок

**Метрики**:
- Number of HTTP 200 for shop API
- Number of HTTP 200 for CRM API
- Number of HTTP 200 for MES API

**Ярлыки**:
- `service`
- `endpoint`

### RabbitMQ метрики (USE)

#### Number of messages in flight in RabbitMQ
**Зачем**: видим backpressure, находим застрявшие очереди

**Ярлыки**:
- `queue`
- `vhost`

#### Number of dead-letter-exchange letters
**Зачем**: видим потерянные сообщения, главная метрика для потери заказов

**Ярлыки**:
- `queue`
- `reason`

### Database метрики (USE)

#### Number of connections для shop db, MES db
**Зачем**: находим connection pool saturation, утечки

**Метрики**:
- Number of connections for shop db instance
- Number of connections for MES db instance

**Ярлыки**:
- `db_instance`
- `state`

#### Memory Utilisation для shop db, MES db
**Зачем**: видим, когда нужно больше памяти для кеша

**Метрики**:
- Memory Utilisation for shop db instance
- Memory Utilisation for MES db instance

**Ярлыки**:
- `db_instance`

#### Size of shop db, MES db instance
**Зачем**: планируем рост дискового пространства

**Метрики**:
- Size of shop db instance
- Size of MES db instance

**Ярлыки**:
- `db_instance`

### Инфраструктурные метрики (USE)

#### CPU % для всех API
**Зачем**: видим saturation, когда нужно масштабирование

**Метрики**:
- CPU % for shop API
- CPU % for CRM API
- CPU % for MES API

**Ярлыки**:
- `service`
- `instance`

#### Memory Utilisation для всех API
**Зачем**: находим memory leaks, планируем ресурсы

**Метрики**:
- Memory Utilisation for shop API
- Memory Utilisation for CRM API
- Memory Utilisation for MES API

**Ярлыки**:
- `service`
- `type`

### Дополнительные метрики (бизнес-метрики)

#### Orders created total
**Зачем**: видим воронку заказов, главная бизнес-метрика

**Ярлыки**:
- `status`
- `source`

#### Orders status duration
**Зачем**: находим где задержки, SLA нарушения

**Ярлыки**:
- `from_status`
- `to_status`
- `quantile`

#### Orders lost total
**Зачем**: считаем заказы, которые не перешли в следующий статус за SLA

**Ярлыки**:
- `stuck_in_status`
- `expected_next_status`

## План действий

### 1. Поднять Prometheus + Grafana
- Поднять Prometheus
- Поднять Grafana для визуализации

### 2. Инструментировать API
**Shop API, CRM API (Java), MES API (C#)**:
- Добавить библиотеки для сбора метрик
- Создать эндпоинт `/metrics` для Prometheus

### 3. Настроить Prometheus
- Настроить сбор метрик с API каждые 15 секунд
- Настроить автопоиск новых инстансов

### 4. Настроить мониторинг RabbitMQ
- Подключить сбор метрик из RabbitMQ
- Метрики: queue depth, DLQ size, consumer lag

### 5. Настроить мониторинг БД
- Подключить сбор метрик из shop-db и mes-db

### 6. Создать дашборды в Grafana
**API дашборд**:
- RPS по сервисам и эндпоинтам
- Latency (p50, p95, p99)
- Error rate за последние 5 минут

**RabbitMQ дашборд**:
- Queue depth для всех очередей
- DLQ size (критичная метрика)
- Consumer lag

**Business дашборд** (для менеджеров):
- Воронка заказов по статусам
- Потерянные заказы за день/неделю
- SLA выполнение (% заказов вовремя)

### 7. Настроить алерты
**Критичные**:
- DLQ > 10 сообщений
- Error rate > 1% за 5 минут
- API latency p95 > 10s
- DB connections > 90%

**Некритичные**:
- Queue depth > 1000
- CPU > 70% за 10 минут
- Memory > 80%

### 8. Добавить бизнес-метрики
- Счетчики заказов по статусам
- Время перехода между статусами
- Счетчик потерянных заказов
