# Анализ архитектуры и проблемные места

## Существующие проблемы

1. **Потеря заказов** - клиенты не получают заказы, потеряны крупные контракты
2. **Нет observability** - не видно, где теряются заказы (логи, метрики, трейсинг)
3. **Медленный дашборд MES** - операторы не могут взять заказы, фильтр/пагинация не помогли
4. **Синхронный расчет цены 2-30 мин** - блокирует API, таймауты у партнеров
5. **Single instance на сервис** - если упадет, система перестанет работать
6. **Одна БД instance на запись/чтение** - узкое место при росте
7. **Shop API и CRM API пишут в Shop DB** - антипаттерн (общая БД)
8. **Ручной deploy в release/prod** - медленно, риск ошибок
9. **E2E тесты только ручные** - задержки релизов

## Потенциальные проблемы

1. **RabbitMQ без гарантий доставки** - вероятно нет publisher confirms, DLQ, acknowledgments (команда делала сама, симптомы указывают)
2. **Нет idempotency в consumers** - могут быть дубли при retry
3. **Нет backpressure** - системы могут перегружать друг друга при пиках
4. **HTTP-кеширование не настроено** - лишние запросы
5. **Нет Circuit Breaker** - риск каскадных падений
6. **Нет rate limiting на API** - риск DDoS от партнеров
7. **Возможно нет индексов в MES DB** - косвенно указывает "пагинация не помогла"

## Инициативы для устранения проблем

### 1. Observability (логи + метрики + трейсинг)
- Логи: ELK, централизованный поиск по order_id
- Трейсинг: Jaeger + OpenTelemetry, traceId через все системы
- Метрики: Prometheus + Grafana (RED)
- Алертинг: на критичные события (DLQ заполнилась, latency >5s)

### 2. RabbitMQ надежная доставка
- Подтверждение отправки
- Ручное подтверждение обработки
- DLQ для сообщений с ошибками
- Retry с увеличением интервала повторной отправки (3 попытки -> DLQ)
- Таблица обработанных сообщений (защита от дублей)

### 3. Оптимизация MES дашборда
- Индексы в БД: составной на (status, created_at DESC)
- Redis для кеша: count по статусам, обновляется каждые 30 сек
- Анализ медленных запросов

### 4. Circuit Breaker между сервисами
- Отключение запросов при падении: Shop -> MES, CRM -> Shop
- Резервные стратегии: показываем из кеша или упрощенную версию

### 5. Масштабирование сервисов
- 2+ инстанса каждого API за балансировщиком
- Реплика БД для чтения
- Health checks и автомасштабирование

### 6. Асинхронный расчет цены
- API сразу отдает 202 Accepted + ID задачи
- Фоновый воркер делает расчет
- Уведомление через webhook
- Таймаут 30 минут

### 7. HTTP-кеширование статики
- Заголовки Cache-Control, ETag для каталога
- CDN для фронтенда
- Ответ 304 Not Modified при совпадении

### 8. API Gateway + Rate Limiting
- Добавить gateway
- Ограничения по API ключу партнера
- Квоты на расчет цены (N запросов/час)

## Приоритизация инициатив
Если можно сделать только 3 пункта:

### 1. Observability (логи + метрики + трейсинг)
- Без этого не решим проблему потери заказов - не знаем, где они теряются
- Нужно ДО фикса RabbitMQ, чтобы проверить, что исправление работает
- Все остальные инициативы требуют observability для проверки

### 2. RabbitMQ надежная доставка + идемпотентность
- Решает корень проблемы - потерю заказов между системами
- После пункта 1 будем видеть, что фикс работает
- Теряем контракты сейчас - прямые потери денег
- Publisher confirms + DLQ + retry = гарантия доставки

### 3. HTTP-кеширование
- Снижает нагрузку на бэкенд и БД
- Простота реализации и быстрый эффект
- Не требует изменения архитектуры
