# Архитектурное решение по трейсингу

## Системы для покрытия трейсингом

**1. Shop API - создание заказа**
- Клиент создает заказ -> Shop API записывает в БД
- Публикует событие в RabbitMQ
- Может зависнуть: timeout при записи в БД, ошибка валидации, RabbitMQ недоступен

**2. MES API - получение заказа**
- Получает сообщение из RabbitMQ
- Может зависнуть: не забрал сообщение, сообщение в DLQ

**3. MES API - расчет цены**
- Рассчитывает стоимость заказа
- Публикует результат в RabbitMQ
- Может зависнуть: timeout расчета, ошибка парсинга 3D-модели, RabbitMQ недоступен

**4. CRM API - получение результата**
- Получает сообщение из RabbitMQ
- Может зависнуть: не забрал сообщение, сообщение в DLQ

**5. CRM API - работа с менеджером**
- Менеджер подтверждает заказ
- Может зависнуть: менеджер не увидел заказ, долго обрабатывает

**6. MES API - производство**
- Оператор берет заказ в работу, производит, упаковывает
- Может зависнуть: оператор не взял, долго производит

**7. Shop DB, MES DB**
- Каждый запрос в БД может быть медленным

### Данные для трейсинга

- `trace_id` - уникальный ID для всего пути заказа
- `span_id` - уникальный ID для конкретного шага
- `parent_span_id` - ID предыдущего шага
- `service_name` - shop-api, crm-api, mes-api, rabbitmq
- `operation_name` - create_order, calculate_price, db_query
- `start_time`, `end_time` - когда началось и закончилось
- `status` - success, error, timeout
- `order_id` - ID заказа
- `user_id` - кто создал заказ
- `order_status` - текущий статус заказа
- `error_message` - если произошла ошибка
- `http.method`, `http.url`, `http.status_code` - для HTTP запросов
- `db.statement` - SQL-запрос (без параметров)
- `rabbitmq.queue` - название очереди
- `file.size` - размер 3D-модели

## Мотивация

**Проблема**: заказы теряются, не знаем где
- Заказы в непонятном состоянии - не видно на каком сервисе застряли
- Сообщения теряются между Shop -> RabbitMQ -> CRM -> MES
- Не можем ответить клиенту "где мой заказ?" - нет истории переходов

**Что даст трейсинг**:
- Видим полный путь заказа от создания до доставки
- Находим узкое место за минуты вместо часов
- Видим, где именно сломалось: Shop не отправил? RabbitMQ потерял? MES не обработал?

**Для бизнеса**:
- Быстрое решение проблем клиентов
- Прозрачность для партнеров
- Уменьшение времени на поиск проблемы
- Видим где теряются заказы

**Метрики, на которые повлияет трейсинг**:

1. **Время решения инцидентов**
   - Было: несколько часов на поиск где застрял заказ
   - Станет: несколько минут с трейсингом
   - Видим всю цепочку за пару кликов

2. **Процент потерянных заказов**
   - Было: не знаем сколько теряем, клиенты жалуются
   - Станет: видим где именно теряются, можем починить
   - Уменьшение количества потерянных заказов

3. **Latency по этапам заказа**
   - Было: не знаем где тормозит
   - Станет: видим latency каждого этапа - где именно медленно
   - Можем оптимизировать узкие места

4. **SLA**
   - Было: обещали 3 недели, не выполняем - не знаем почему
   - Станет: видим где задержки, можем улучшить процесс
   - Ожидаем рост SLA выполнения

5. **Лояльность клиентов**
   - Было: клиенты недовольны - не видят статус заказа
   - Станет: можем показывать статус в реальном времени
   - Ожидаем рост повышение лояльности клиентов


## Предлагаемое решение

### Технологии

**Jaeger** - система для трасировки
- Open source, проверенное решение
- Визуализация трейсов, поиск по trace_id и order_id

**OpenTelemetry** - библиотеки для инструментирования
- Стандарт для трейсинга (раньше OpenTracing)
- Поддержка Java, C#, Python
- Автоматическое инструментирование HTTP, gRPC, БД

### Компоненты решения

**1. OpenTelemetry SDK в каждом API**
- Shop API (Java): добавить библиотеку OpenTelemetry
- CRM API (Java): добавить библиотеку OpenTelemetry
- MES API (C#): добавить библиотеку OpenTelemetry

**2. Jaeger**
- Принимает spans от всех агентов
- Валидирует и сохраняет в хранилище
- Можно масштабировать горизонтально

**3. Jaeger UI**
- Web-интерфейс для поиска трейсов
- Показывает timeline всех spans
- Фильтры по сервису, статусу, latency

### Передача trace_id через систему

**HTTP-запросы**:
- trace_id передается в заголовке `X-Trace-Id`
- OpenTelemetry автоматически извлекает и продолжает trace

**RabbitMQ**:
- trace_id добавляется в message properties (headers)
- Consumer извлекает и продолжает trace
- Пример:
  ```
  headers: {
    "trace_id": "abc123...",
    "parent_span_id": "span456..."
  }
  ```

**База данных**:
- trace_id можно логировать в отдельную таблицу (опционально)
- Или просто тегать SQL-запросы в span

## Компромиссы

### Где трейсинг не принесет пользы или пока невозможен

**1. Фронтенд (Vue, React)**
- Можно добавить browser tracing, но сложно и польза мала - фронтенд не участвует в потере заказов

**2. Внешние партнеры (API клиенты)**
- Не можем заставить партнеров использовать наш trace_id

**3. Транспортная компания**
- Внешняя система, нет API для трейсинга

**4. S3 хранилище**
 - Низкая польза, так как не влияет на потерю заказов

## Безопасность

### Меры предотвращения несанкционированного доступа

**1. Аутентификация в Jaeger UI**
- Доступ только для сотрудников поддержки и разработчиков
- Интеграция с корпоративным сервисом аутентификации
- Закрыть публичный доступ из интернета

**2. Сетевая изоляция**
- Jaeger, Jaeger UI - только во внутренней сети (VPC)
- Нет доступа из интернета
- Firewall rules: только API могут отправлять в Jaeger

**3. Шифрование данных**
- Spans передаются по HTTPS

**4. Скрытие чувствительных данных**
- Не логируем в трейсинг:
  - Пароли, токены, API ключи
  - Персональные данные (телефон, email) - только user_id
  - Полные SQL-запросы с параметрами (могут быть секретными)
- Заменяем чувствительные поля на `***`

**5. Retention policy**
- Трейсы хранятся 30 дней, потом автоматически удаляются

**6. Audit log**
- Логируем кто и когда смотрел трейсы в Jaeger UI
- Алерт при подозрительной активности

**7. Rate limiting**
- Ограничение на количество spans от одного API
- Если API начнет отправлять блокируем соединение

**8. RBAC (Role-Based Access Control)**
- Роль "Support": может смотреть трейсы, искать по order_id
- Роль "Developer": может смотреть + экспортировать данные
- Роль "Admin": полный доступ к Jaeger
